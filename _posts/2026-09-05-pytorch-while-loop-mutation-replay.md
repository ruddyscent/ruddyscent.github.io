함수를 컴파일한 뒤 원래 함수와 반환값을 비교해 결과가 같다면, 컴파일러가 함수를 올바르게 변환한다고 판단해도 될까요?

입력을 직접 바꾸는 함수라면 반환값만으로는 알 수 없습니다. 입력 텐서(tensor)에 남겨야 할 상태가 다를 수 있기 때문입니다. 첫 호출에서 드러나지 않는 오류가 두 번째 호출부터 나타나기도 합니다.

PyTorch의 [Issue #195327](https://github.com/pytorch/pytorch/issues/195327)은 이런 사례입니다. 이슈에서 다루는 버전에서는 `torch.while_loop`의 조건 함수가 외부 텐서를 변경해도 특정 Inductor 경로가 그 변경을 호출자의 텐서에 제대로 반영하지 못합니다. [PR #195393](https://github.com/pytorch/pytorch/pull/195393)은 조건 함수와 본문 양쪽의 변경을 분석해 스케줄러(scheduler)에 알리는 방식으로 문제를 다룹니다.

이 글에서는 작은 수치 예제로 현상을 따라간 뒤 제어 흐름 연산자, 함수형 변환(functionalization), 부수 효과 분석, 연산의 실행 순서를 정하는 의존성, 회귀 테스트 설계를 살펴봅니다. 파이썬 함수와 반복문을 바탕으로 설명하겠습니다.

## 1. 반환값만 같으면 올바른 실행일까?

먼저 작은 사전으로 생각해 보겠습니다.

```python
def step(box):
    box["value"] *= 0.5
    return box["value"]

box = {"value": 1.0}
answer = step(box)
```

호출 후에는 두 가지를 확인할 수 있습니다.

- `answer`는 `0.5`입니다.
- `box["value"]`도 `0.5`입니다.

어떤 변환이 반환값만 `0.5`로 만들고 사전은 `1.0`으로 남겨 둔다면 원래 함수와 같지 않습니다. 다음 호출의 출발점이 달라집니다.

상태가 있는 함수를 식으로 나타내면 다음과 같습니다.

```text
F(입력, 이전 상태) = (반환값, 다음 상태)
```

여기에는 **상태 전이(state transition)**라는 개념이 들어 있습니다. 함수 호출 한 번을 이전 상태에서 다음 상태로 넘어가는 과정으로 보는 것입니다. 사전 예제에서는 `box["value"]`가 상태이고, `step()`을 호출할 때마다 그 값이 절반으로 바뀝니다. 같은 객체를 다시 호출하면 앞선 호출의 다음 상태가 이번 호출의 이전 상태가 됩니다.

컴파일러는 반환값과 다음 상태를 모두 보존해야 합니다. 반환값만 비교하면 함수의 동작 일부만 검사하는 셈입니다. 호출자가 확인할 수 있는 결과가 모두 같아야 한다는 조건을 **관찰 가능한 동작의 동등성(observational equivalence)**이라고 합니다.

## 2. 제어 흐름 연산자: 반복문을 하나의 연산으로 표현하기

보통 파이썬 반복문은 조건을 검사하고 본문을 실행합니다. `torch.while_loop`는 이를 조건 함수와 본문 함수로 나눕니다.

```python
def cond(i, acc):
    return i < 2

def body(i, acc):
    return i + 1, acc + 1

i, acc = torch.while_loop(cond, body, (initial_i, initial_acc))
```

개념적인 실행 방식은 다음과 같습니다.

```python
values = initial_values
while cond(*values):
    values = body(*values)
return values
```

`torch.while_loop`처럼 함수를 인자로 받는 연산을 **고차 연산자(higher-order operator, HOP)**라고 부릅니다. 컴파일러는 인자로 받은 조건 함수와 본문 함수를 각각 하위 그래프로 표현하고, 이 두 그래프를 사용하는 `while_loop` 연산 하나로 반복 구조를 다룹니다.

### 반복 전달 입력과 외부 텐서

여기에는 서로 다른 종류의 입력이 있습니다.

| 종류 | 예 | 역할 |
|---|---|---|
| 반복 전달 입력(carried inputs) | `i`, `acc` | 본문의 반환값으로 다음 반복의 값을 정한다 |
| 외부에서 참조하는 텐서(captured tensors) | 바깥 함수의 `state` | 클로저(closure)가 참조하며, 내부적으로 추가 입력(additional inputs)이 될 수 있다 |

**클로저**는 함수가 자신을 정의한 바깥 함수의 변수에 접근할 수 있도록 그 참조 환경을 함께 유지하는 함수입니다. 다음은 외부 텐서를 참조하는 조건 함수를 만드는 예입니다.

```python
def make_cond(state):
    def cond(i, acc):
        state.mul_(0.5)
        return i < 2

    return cond
```

`cond`는 `i`, `acc`만 인자로 받지만 바깥 함수 `make_cond`의 `state`에도 접근합니다. `make_cond`가 실행을 마치고 `cond`를 반환한 뒤에도 이 참조를 유지합니다. 따라서 `cond`를 호출할 때마다 `state`를 인자로 다시 넘길 필요가 없습니다.

이때 텐서를 자동으로 복제하지는 않습니다. `cond`가 같은 텐서를 참조하므로 `state.mul_(0.5)`는 호출자가 넘긴 텐서 자체의 값을 바꿉니다. 반복 전달 입력에 없는 텐서도 조건 함수나 본문에서 변경할 수 있는 이유입니다.

조건과 본문이 받아 쓰는 값이 모두 반복 전달 입력인 것은 아닙니다. 외부에서 참조하는 텐서의 제자리 변경(mutation)은 별도로 등록해야 하는데, 뒤에서 그 이유를 살펴보겠습니다.

분석 대상 버전의 [`while_loop` 제약 사항](https://github.com/pytorch/pytorch/blob/e4d9b6187e6ef2635cc2b648fbb409d25d6a9d9a/torch/_higher_order_ops/while_loop.py#L192-L209)은 조건 함수와 본문이 반복 전달 입력을 직접 변경하는 것을 금지합니다. 같은 설명에서 추론 중에는 반복 전달 입력이 아닌 외부 텐서를 변경할 수 있다고 명시합니다. 이 글에서 다루는 `state`의 변경은 이 허용 범위에 해당합니다. 모든 입력의 제자리 변경이나 학습 모드까지 허용한다는 뜻은 아닙니다.

같은 제약 사항은 조건 함수와 본문이 외부 파이썬 사전이나 리스트를 변경하는 것도 금지합니다. 1절의 사전 예제는 반환값과 호출 후 상태를 구분하기 위한 개념 설명용입니다.

## 3. 실제 사례: 조건 함수에서 외부 텐서 변경하기

이슈의 핵심을 간추리면 다음과 같습니다. 아래 코드는 `torch`를 가져온 뒤 추론 모드인 `torch.inference_mode()`에서 호출하는 함수입니다.

```python
def f(state):
    state.mul_(0.8)

    def cond(i, acc):
        state.mul_(0.5)
        return i < 2

    def body(i, acc):
        return i + 1, acc + state

    i, acc = torch.while_loop(
        cond,
        body,
        (
            torch.zeros((), dtype=torch.int64, device=state.device),
            torch.zeros_like(state),
        ),
    )
    return i, acc, state.clone()
```

`mul_`는 텐서의 값을 제자리에서 바꿉니다. 새 결과를 반환하는 `mul`과 달리 원래 입력에도 변경이 남습니다. 마지막의 `state.clone()`은 새 저장 공간을 만들어 현재 값을 복제하므로, 반환된 복제본과 호출자가 가진 원래 텐서를 따로 확인할 수 있습니다.

### 마지막 조건 검사까지 따라가기

`state`의 초깃값을 `1.0`이라고 하겠습니다. 소수 계산을 간단히 표시하면 다음 순서입니다.

| 단계 | `i` | 조건 결과 | `state` | `acc` |
|---|---:|---|---:|---:|
| 루프 전 `× 0.8` | 0 | — | 0.8 | 0 |
| 첫 조건 `× 0.5` | 0 | 참 | 0.4 | 0 |
| 첫 본문 | 1 | — | 0.4 | 0.4 |
| 둘째 조건 `× 0.5` | 1 | 참 | 0.2 | 0.4 |
| 둘째 본문 | 2 | — | 0.2 | 0.6 |
| 마지막 조건 `× 0.5` | 2 | 거짓 | 0.1 | 0.6 |

반복문은 본문을 두 번 실행하지만 조건을 세 번 검사합니다. 마지막 조건의 결과가 거짓이어도 그 조건 함수 안에서 이미 수행한 제자리 변경은 사라지지 않습니다.

일반적으로 정상 종료하는 while 루프는 본문을 N번 실행하면 조건을 N+1번 평가합니다. 이 예제의 호출당 최종 상태는 다음과 같습니다.

```text
다음 상태 = 이전 상태 × 0.8 × 0.5³
          = 이전 상태 × 0.1
```

첫 호출 후 `0.1`, 두 번째 호출 후 `0.01`이어야 합니다. 누적값은 각 호출 시작 상태의 `0.6`배이므로 각각 약 `0.6`, `0.06`입니다. 실제 부동소수점 표시는 약간 다를 수 있습니다.

### 본문을 실행하지 않는 경우

조건이 처음부터 거짓인 경우도 생각해 볼 수 있습니다. 반복문은 본문을 실행하지 않지만 조건을 한 번 검사합니다. 이때 최종 상태는 `1.0 × 0.8 × 0.5 = 0.4`입니다. 본문을 실행하지 않아도 조건 함수에서 상태를 변경합니다.

## 4. 첫 호출은 맞는데 다음 호출이 틀리는 이유

이슈가 제시한 [재현 코드와 실행 출력](https://github.com/pytorch/pytorch/issues/195327)에서 반환값과 호출자에게 남는 상태를 확인할 수 있습니다. 수치를 반올림해 비교하면 다음과 같습니다.

| 실행 방식 | 호출 | 반환된 누적값 | 반환된 상태 복제본 | 호출자에게 남은 상태 |
|---|---:|---:|---:|---:|
| 즉시 실행(eager) / `aot_eager` | 1 | 0.6 | 0.1 | 0.1 |
| 즉시 실행 / `aot_eager` | 2 | 0.06 | 0.01 | 0.01 |
| 이슈에서 다루는 Inductor | 1 | 0.6 | 0.1 | 0.8 |
| 이슈에서 다루는 Inductor | 2 | 0.48 | 0.08 | 0.64 |

첫 호출에서는 반환된 상태 복제본까지 맞습니다. 하지만 외부 텐서는 루프 직전 값인 `0.8`로 남습니다. 두 번째 호출은 이 잘못된 상태에서 시작하므로 누적값이 `0.06`이 아니라 `0.48`이 됩니다.

내부 계산에 사용하는 값과 외부 저장 공간에 반영하는 값이 달라지는 버그입니다. 상태를 다음 단계에 사용하는 시뮬레이션이나 반복 갱신에서 특히 놓치기 쉽습니다.

### 점화식으로 반복 호출의 상태 계산하기

호출자가 가진 상태가 매번 올바르게 바뀌는지는 **점화식(recurrence relation)**으로 확인할 수 있습니다. 점화식은 앞의 값을 이용해 다음 값을 정하는 식입니다. `s_k`를 함수를 k번 호출한 뒤의 상태, `s_0`를 처음 상태라고 두면 다음과 같습니다.

```text
s_(k+1) = 0.1 × s_k
s_k     = s_0 × (0.1)^k
```

매번 같은 비율을 곱하므로 상태의 나열은 공비가 `0.1`인 **등비수열(geometric sequence)**입니다. 처음 상태가 `1.0`이면 `1.0 → 0.1 → 0.01 → 0.001`로 변합니다. 여기서 k는 함수 호출 횟수이며, 한 번의 호출 안에서 본문을 실행하는 횟수와 구분해야 합니다. 이 식은 부동소수점 반올림을 제외한 수학적 계산입니다.

본문 실행 횟수를 매 호출마다 N번으로 고정하면 공비는 `0.8 × (0.5)^(N+1)`입니다. 조건을 마지막에 한 번 더 검사하므로 지수가 N이 아니라 N+1입니다. 반복 횟수를 바꾼 테스트에서도 이 식으로 기대 상태를 계산할 수 있습니다.

## 5. 함수형 변환: 계산한 값을 원래 입력에 다시 복사하기

컴파일러는 입력을 직접 바꾸는 연산을 분석하기 위해 제자리 변경을 함수형 값의 흐름으로 바꿀 수 있습니다. 앞서 언급한 함수형 변환입니다.

원래 코드가 다음과 같다면:

```python
state.mul_(0.8)
```

개념적으로 다음처럼 생각할 수 있습니다.

```python
base = state * 0.8
# Work on base.
state.copy_(base)
```

새로운 값인 `base`를 사용하면 중간 계산을 분석하기 편합니다. 계산을 마친 뒤에는 호출자가 전달한 원래 텐서에 다시 복사(copy-back)해야 합니다. `copy_`는 `clone()`처럼 새 저장 공간을 만드는 대신 기존 텐서의 저장 공간에 값을 씁니다.

[PR의 원인 분석](https://github.com/pytorch/pytorch/pull/195393)은 사전 컴파일(ahead-of-time compilation, AOT) 이후 `auto_functionalized_v2`가 루프를 감싸며 계산된 기준 텐서(computed base)를 관리하는 과정을 설명합니다. 이후 Inductor가 이를 일반 `while_loop`로 되돌리는 과정에서는 어느 입력을 변경하는지 나타내는 정보를 연산 노드에 그대로 전달하지 않습니다. 따라서 하위 표현으로 변환하는 단계(lowering)에서 조건 함수와 본문의 하위 그래프를 검사해 제자리 변경 정보를 다시 구해야 합니다.

루프 이전의 `state.mul_(0.8)`은 외부 텐서와 별도로 계산된 기준 텐서가 생기는 경로를 드러냅니다. 겉보기에 불필요한 한 줄을 재현 코드에서 제거하면 실패 조건까지 사라질 수 있습니다.

각 컴파일 단계가 값과 함께 변경 정보도 다음 단계로 전달하는지 확인해야 합니다.

## 6. 쓰기 의존성: 복사를 루프 뒤에 실행해야 하는 이유

컴파일러의 스케줄러는 연산을 재배치하거나 합칠 수 있습니다. 단, 프로그램의 의존성을 보존해야 합니다.

이 예제에서 필요한 순서는 다음과 같습니다.

```text
P: base를 계산한다
L: 루프가 base를 읽고 변경한다
C: 최종 base를 외부 state로 복사한다

P → L → C
```

이 도식은 **방향 그래프(directed graph)**입니다. P, L, C를 각각 노드로 보고, 한 연산이 끝나야 다른 연산을 수행할 수 있다는 관계를 화살표로 표시합니다. 여기서는 반복문 전체를 L이라는 노드 하나로 묶어 루프 바깥의 의존성만 나타냅니다.

연산의 선후 관계는 **부분 순서(partial order)**로 이해할 수 있습니다. 의존 관계가 있는 연산끼리는 순서를 지켜야 하지만, 그런 관계가 없는 두 연산의 순서까지 정할 필요는 없습니다. 위 그래프에서는 P가 L보다 앞서고 L이 C보다 앞서므로 P도 C보다 앞서야 합니다.

그런데 컴파일러가 루프를 `base`를 읽기만 하는 연산으로 기록하면 스케줄러가 보는 그래프는 달라집니다.

```text
P → L
P → C
```

두 번째 그래프에는 L의 쓰기가 끝난 다음 C가 읽어야 한다는 연결이 없습니다. PR의 원인 설명에 따르면 스케줄러는 이 때문에 원래 입력에 다시 복사하는 연산을 루프 이전 연산 함수(커널, kernel)에 합칩니다. 그 결과 이 연산 함수는 사용자 텐서에 오래된 값을 기록합니다.

### 위상 정렬과 실행 순서

방향을 따라 순환하지 않는 그래프에서 화살표의 선후 관계를 지키도록 노드를 나열하는 알고리즘이 **위상 정렬(topological sorting)**입니다. `P → L → C`에서는 `P, L, C` 순서를 따라야 합니다. 반면 `P → L`, `P → C`만 있으면 `P, L, C`와 `P, C, L` 모두 그래프의 제약을 만족합니다. 쓰기 의존성을 하나 빠뜨리면 그래프상으로 허용하는 실행 순서가 달라집니다.

파이썬의 [`graphlib.TopologicalSorter` 문서](https://docs.python.org/3.10/library/graphlib.html)는 의존 관계를 입력해 위상 정렬 순서를 구하는 예제를 제공합니다. 두 그래프의 가능한 순서를 직접 비교하며 공부할 수 있습니다. 이는 실행 순서의 제약을 이해하기 위한 연결이며, Inductor가 이 파이썬 클래스를 사용한다는 뜻은 아닙니다. 실제 스케줄러는 연산 융합과 실행 비용도 함께 고려합니다.

컴파일러가 중간 표현(intermediate representation, IR)에 변경 의존성을 기록하지 않아 생기는 순서 문제입니다. 컴파일러가 변경을 기록하지 않으면 의존성을 지켰다고 판단한 실행 순서도 실제로는 잘못될 수 있습니다.

스케줄러는 이처럼 부수 효과를 기록한 메타데이터(metadata)를 바탕으로 올바른 실행 순서를 결정합니다.

## 7. 변경 정보 등록: 기존 저장 공간의 쓰기를 표현하기

Inductor는 `MutationOutput`으로 연산이 기존 버퍼(buffer)를 변경한다는 사실을 나타냅니다. 새 텐서를 사용자에게 반환하는 일반 출력과 역할이 다릅니다.

다음은 실제 API 호출을 옮긴 코드가 아니라, 핵심 동작을 요약한 설명용 코드입니다.

```python
mark_buffer_mutated(mutated_buffer_name)
record_mutating_operation(while_loop)
```

실제 [`MutationOutput` 구현](https://github.com/pytorch/pytorch/blob/88db2f793a1ba3530bd13a45f5988bc219f9e714/torch/_inductor/ir.py#L8374-L8396)을 보면 생성자에서 `mark_buffer_mutated()`로 변경을 등록하고, `should_allocate()`는 `False`를 반환합니다. 새로운 데이터 버퍼를 할당하지 않고 기존 버퍼의 변경을 중간 표현에 기록하는 구조입니다.

루프가 명시적으로 반환하는 것은 `i`, `acc`입니다. 하지만 `state`도 바뀝니다. 본문 반환값만 순회해 출력을 등록하면 외부에서 참조하는 텐서의 변경을 놓칠 수 있습니다.

값 출력과 효과 출력의 차이는 다음과 같습니다.

```text
값 출력:    함수가 어떤 값을 반환하는가?
효과 출력:  함수가 어떤 기존 저장 공간을 바꾸는가?
```

효과 출력은 반환 튜플(tuple)에 없어도 추적해야 합니다. 관련 선행 작업인 [PR #184164](https://github.com/pytorch/pytorch/pull/184164)는 본문이 빈 튜플 `()`을 반환하는 반복문에서도 버퍼 변경을 `MutationOutput`으로 등록하는 문제를 다룹니다.

## 8. 개선된 알고리즘: 조건과 본문의 변경 집합 합치기

기존 코드는 `body_fn`에서 변경한 입력의 위치 번호만 수집합니다. 조건 함수에서만 변경한 외부 텐서는 이 목록에 없습니다.

### 두 하위 그래프의 쓰기 가능성 분석

PR은 다음처럼 양쪽을 분석합니다. 아래 코드는 설명을 위해 단순화했습니다.

```python
mutated = OrderedSet()
for subgraph in (cond_fn, body_fn):
    mutated |= mutations_of(subgraph)
```

수학적으로는 다음과 같습니다.

```text
M_loop = M_cond ∪ M_body
```

`M_cond`와 `M_body`는 각각 조건 함수와 본문이 변경할 수 있는 입력의 위치 번호를 담은 집합입니다. `∪`는 두 집합 중 어느 한쪽에라도 있는 원소를 모으는 **합집합(union)** 기호입니다. 두 함수가 같은 입력을 변경해도 결과 집합에는 그 위치 번호를 한 번만 넣습니다.

코드를 실행하기 전에 어떤 값을 읽거나 바꿀 수 있는지 조사하는 작업을 **정적 분석(static analysis)**이라고 합니다. 이 중 **쓰기 가능성 분석(may-write analysis)**은 실행 중 변경할 가능성이 있는 입력을 모읍니다. 여기서는 두 하위 그래프에서 얻은 집합을 합쳐 루프 전체의 쓰기 가능성을 요약합니다.

예를 들어 전체 입력에서 위치 번호가 2인 추가 입력을 조건이 쓰고, 위치 번호가 3인 추가 입력을 본문이 쓰면 다음과 같습니다.

```text
M_cond = {2}
M_body = {3}
M_loop = {2, 3}
```

두 함수가 모두 변경하는 입력만 남기는 교집합을 사용하면 조건 함수에서만 바꾸는 `state`를 놓칩니다. 반대로 본문을 한 번도 실행하지 않는 경우에도 이 분석은 본문에서 수행할 수 있는 쓰기를 요약에 포함할 수 있습니다. 스케줄러는 이 정보를 바탕으로 의존 관계가 있는 연산의 이동을 보수적으로 제한합니다. 쓰기 가능성을 기록한다고 본문을 실제로 실행하는 것은 아닙니다.

더 공부하려면 [Cornell의 데이터 흐름 분석 강의](https://www.cs.cornell.edu/courses/cs6120/2023fa/lesson/4/)에서 여러 경로의 분석 결과를 합치는 과정을 살펴볼 수 있습니다. 이 PR에서는 두 하위 그래프에서 얻은 변경 집합을 합치는 부분이 그와 연결됩니다.

효과 분석에서 쓰기를 빠뜨리면 잘못된 결과가 생길 수 있습니다. 반대로 과도하게 포함하면 최적화 기회를 줄일 수 있습니다. 정확성을 지키는 보수성과 최적화 기회를 살리는 정밀도 사이에서 균형을 찾아야 합니다.

### 추가 입력의 변경 등록

PR은 합집합을 구한 뒤 반복 전달 입력 다음에 놓인 추가 입력에 별도로 `MutationOutput`을 등록합니다.

```python
for idx in sorted(mutated):
    if idx >= len(carried_inputs):
        register_mutation(all_inputs[idx], while_loop)
```

실제 [`WhileLoop.create`의 변경 처리 코드](https://github.com/pytorch/pytorch/blob/88db2f793a1ba3530bd13a45f5988bc219f9e714/torch/_inductor/ir.py#L11795-L11865)에서는 앞부분의 `for subgraph in (cond_fn, body_fn)`이 두 하위 그래프의 변경을 수집합니다. 뒤의 `if idx >= len(carried_inputs)`는 추가 입력을 골라 `MutationOutput`을 등록합니다. 조건의 쓰기를 발견하는 것과 발견한 쓰기를 외부 그래프에 알리는 것, 두 단계가 모두 필요합니다.

### 입력의 위치 번호로 연결하기

PR은 제자리 변경 목록을 순회하는 반복자(iterator) 대신 [`all_inputs[idx]`로 입력을 직접 선택](https://github.com/pytorch/pytorch/blob/88db2f793a1ba3530bd13a45f5988bc219f9e714/torch/_inductor/ir.py#L11833-L11841)하도록 바꿉니다.

변경 분석 결과가 `[2, 0]` 순서라고 가정하겠습니다. 변경된 버퍼 목록도 `[input2, input0]`가 됩니다. 그런데 출력 루프가 `0, 1, 2` 순서로 돌면서 다음 코드를 실행하면 어떻게 될까요?

```python
if idx in mutated:
    mutated_input = next(mutated_inputs_iter)
```

`idx == 0`일 때 `input2`를 꺼내 잘못 연결할 수 있습니다.

위치 번호로 입력을 직접 선택하면 두 목록의 순서가 같다고 전제할 필요가 없습니다.

```python
mutated_input = all_inputs[idx]
```

`OrderedSet`은 발견 순서를 보존할 뿐 위치 번호의 오름차순으로 정렬하지는 않습니다. 분석 함수는 [그래프 노드를 순회하며 제자리 변경을 수집](https://github.com/pytorch/pytorch/blob/88db2f793a1ba3530bd13a45f5988bc219f9e714/torch/_higher_order_ops/utils.py#L1129-L1142)하므로 입력의 위치 번호 순서와 일치한다고 가정해서는 안 됩니다.

입력의 위치 번호로 대상을 찾는 방식은 **직접 주소 지정(direct addressing)**과 연결됩니다. 이때 유지해야 할 **불변조건(invariant)**은 “변경 집합의 번호 idx가 가리키는 입력은 항상 `all_inputs[idx]`다”입니다. 불변조건은 알고리즘의 각 단계에서 유지해야 하는 성질로, 여기서는 변경을 발견한 순서와 관계없이 올바른 입력을 선택하는 기준입니다.

## 9. 테스트는 반환값과 다음 호출의 상태를 함께 검증해야 한다

이 버그를 검사하려면 반환값과 상태를 함께 비교해야 합니다.

### 반환값과 외부 상태가 같은가?

```python
expected = eager(state_eager)
actual = compiled(state_compiled)

assert_outputs_equal(expected, actual)
assert_states_equal(state_eager, state_compiled)
```

### 같은 객체로 다시 호출해도 올바른가?

같은 객체로 여러 번 호출하는 검사도 필요합니다. 호출할 때마다 상태를 초기화하면 누적 오류를 숨길 수 있습니다.

### 어떤 경계 조건을 검사하는가?

PR이 추가한 테스트는 다음 경계를 다룹니다.

- 조건만 변경, 본문만 변경, 양쪽 모두 변경
- 루프에 들어가기 전 외부에서 참조하는 텐서 변경
- 본문 실행 횟수 0회
- 같은 상태로 여러 번 호출
- 일부 테스트의 동적/정적 형태 설정(`dynamic`/`static`)
- 장치에 공통으로 적용하는 CPU/CUDA 검사

[PR 작성자의 실행 기록](https://github.com/pytorch/pytorch/pull/195393)은 새 테스트 18개 실행 사례가 수정 전 실패하고 수정 후 통과했다고 보고합니다. [반복 호출 테스트](https://github.com/pytorch/pytorch/blob/88db2f793a1ba3530bd13a45f5988bc219f9e714/test/functorch/test_control_flow.py#L12650-L12749)는 같은 상태로 세 번 호출하며 반환값과 외부 텐서를 매번 비교합니다. 다만 이 테스트에는 `dynamic` 설정을 바꿔 실행하는 매개변수화가 없으므로, 모든 설정의 완전한 조합을 검사하는 것은 아닙니다.

`eager`, `aot_eager`, `inductor` 비교도 유용합니다. 이슈에서 앞의 두 실행 방식이 일치하고 Inductor만 달랐다는 사실은 조사 범위를 좁히는 단서입니다. 다만 이것만으로 특정 소스 줄을 원인으로 단정할 수는 없습니다. 중간 그래프와 제자리 변경 의존성을 함께 봐야 합니다.

## 10. 변경 집합과 반환값 선택을 구분해야 하는 이유

앞의 테스트는 외부 텐서 변경을 검사합니다. 이 결과만으로 변경 집합을 사용하는 모든 경로를 검증했다고 볼 수는 없습니다. PR에 추가된 AI 리뷰는 합집합의 사용 범위에 우려를 제기했습니다. 구현이 제자리 변경 집합의 합집합을 추가 입력의 효과 등록과 반복 전달 출력 구성에 함께 사용하기 때문입니다.

[AI 리뷰 원문](https://github.com/pytorch/pytorch/pull/195393#issuecomment-5518536425)은 테스트를 실행하지 못한 채 코드를 읽고 분석한 의견임을 밝힙니다. 해당 경로에 실제로 도달할 수 있는지도 추가 확인이 필요하다고 명시합니다. 새로운 결함이 확정됐다고 받아들이면 안 됩니다.

이 의견에서 구분해야 할 질문은 다음 두 가지입니다.

```text
어느 하위 그래프든 버퍼를 쓰는가?
루프가 다음 반복으로 전달하고 반환해야 할 값은 무엇인가?
```

첫 질문에 적합한 보수적인 합집합이 두 번째 질문의 답으로도 적합한지는 별도로 확인해야 합니다. 집합을 넓힐 때는 그 집합을 읽는 모든 코드를 점검해야 합니다.

특히 반복 전달 입력의 제자리 변경에는 공개 소스에 명시된 제약이 있습니다. 허용된 외부 텐서 변경을 고치는 과정에서 금지된 입력 변경의 처리 경로에도 영향을 주는지는 실제 재현과 오류 검사 테스트로 확인해야 합니다. 이 글에서는 그 부분을 검증하지 않았습니다.

## 맺음말

반복문을 컴파일할 때는 조건 함수의 마지막 평가, 외부 저장 공간에 남는 변경, 다음 호출의 시작 상태까지 보존해야 합니다.

```text
조건 함수와 본문의 제자리 변경
              │
              ▼
두 하위 그래프의 변경 집합 분석
              │
              ▼
추가 입력의 MutationOutput 등록
              │
              ▼
루프가 끝난 뒤 원래 입력에 다시 복사
              │
              ▼
다음 호출에서 변경한 상태 사용
```
