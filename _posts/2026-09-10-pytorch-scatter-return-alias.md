함수가 돌려준 결과를 수정했는데 함수에 넣었던 입력까지 바뀐다면 어떨까요? 원래 두 값이 같은 메모리를 공유하도록 만든 프로그램이라면 자연스러운 동작입니다. 하지만 각각 따로 보관해야 하는 값이었다면 잘못된 결과입니다.

[PyTorch 이슈 #195451](https://github.com/pytorch/pytorch/issues/195451)에서는 컴파일한 함수에서만 이런 일이 일어났습니다. 함수 호출 직후의 텐서(tensor) 값은 정확했습니다. 반환값을 수정하고 나서야 입력도 함께 바뀐다는 사실이 드러났습니다.

이 문제를 이해하려면 계산 결과와 함께 **그 결과가 어느 메모리에 들어 있는지**도 살펴봐야 합니다. 작은 예제로 메모리 공유와 재사용을 이해한 뒤, [PR #195484](https://github.com/pytorch/pytorch/pull/195484)가 어떤 검사를 추가하는지 따라가 보겠습니다.

> 이 글은 2026년 9월 3일 확인한 PR의 커밋 `316140e0fecca99b2133b9d0cb95f8de34213c7a`를 기준으로 합니다. 당시 PR은 열린 상태였습니다. 아래 버그 증상과 테스트 결과는 이슈·PR 작성자의 보고이며, 이 글을 위해 PyTorch 재현 코드나 회귀 테스트를 새로 실행하지는 않았습니다.

## 1. 원래 함수는 무엇을 해야 할까?

이슈에서 문제가 된 함수는 다음과 같습니다.

```python
import torch


def fn(x, src):
    updated = torch.slice_scatter(x, src, 0, 0, 1)
    x.copy_(updated)
    return updated
```

`x`에 `[1, 2]`, `src`에 `[10]`이 들어 있다고 해 보겠습니다. 첫 줄의 `slice_scatter`는 `x`의 일부를 `src`로 바꾼 **새 텐서**를 만듭니다. 이 예제에서는 첫 번째 원소를 바꾸므로 `updated`는 `[10, 2]`가 됩니다. 이 시점의 `x`는 여전히 `[1, 2]`입니다.

다음 줄의 `x.copy_(updated)`는 `updated`의 값을 기존 `x`의 저장 공간에 복사합니다. 이제 두 텐서에 같은 값이 들어 있지만 저장 공간은 각각 따로 있습니다. 마지막 줄은 그중 `updated`를 반환합니다.

```text
실행 전                 새 결과 생성              입력에 다시 복사
x       [1, 2]          x       [1, 2]            x       [10, 2]
                        updated [10, 2]           updated [10, 2]
                                                  ↑ 서로 독립적인 저장 공간
```

따라서 함수 밖에서 반환값을 바꾸더라도 `x`는 바뀌지 않아야 합니다. 반환값에 `add_(100)`을 적용하면 반환값만 `[110, 102]`가 되고 `x`는 `[10, 2]`로 남아야 합니다.

여기서 `add_`는 텐서 자체의 값을 직접 바꾸는 **제자리 연산(in-place operation)**입니다. `add`가 덧셈 결과를 새 텐서로 만드는 것과 구분해야 합니다.

그런데 이슈에서 보고한 컴파일된 실행(compiled execution)은 이 기대와 달랐습니다. 컴파일하지 않고 실행하는 즉시 실행(eager execution)과 비교하면 차이가 보입니다.

| 관찰 시점 | 즉시 실행의 `x` | 문제가 있던 컴파일된 실행의 `x` |
| --- | --- | --- |
| 함수 호출 직후 | `[10, 2]` | `[10, 2]` |
| 반환값에 `add_(100)` 후 | `[10, 2]` | `[110, 102]` |

계산을 틀린 것은 아닙니다. 컴파일 과정에서 원래 독립적이던 입력과 반환값이 같은 저장 공간을 쓰게 된 것이 문제입니다. [이슈의 재현 코드와 출력](https://github.com/pytorch/pytorch/issues/195451)

## 2. 별칭은 같은 메모리를 함께 쓰는 관계다

서로 다른 텐서가 같은 저장 공간을 공유하는 관계를 **별칭(alias)**이라고 부릅니다. 이름이나 객체가 다르다고 값이 들어 있는 메모리까지 다른 것은 아닙니다.

예를 들어 텐서의 일부를 잘라 만든 뷰(view)는 원본의 저장 공간을 공유합니다.

```python
x = torch.tensor([1.0, 2.0, 3.0])
y = x[1:]
```

`y`는 `[2, 3]`에 해당하는 부분을 바라봅니다. `y`의 첫 원소를 바꾸면 `x`의 둘째 원소도 바뀝니다. 반면 `z = x.clone()`은 새 저장 공간을 만들어 값을 복제하므로 `z`를 바꿔도 `x`에 영향을 주지 않습니다. 앞 절의 `copy_`가 이미 있는 저장 공간에 값을 복사하는 것과도 다릅니다.

처음 예제로 돌아가면 함수가 끝난 뒤의 관계는 다음과 같아야 합니다. 여기서 `out`은 호출자가 받은 반환값입니다.

```text
원래 동작                         문제가 된 동작
x   → 저장 공간 A [10, 2]          x   ─┐
out → 저장 공간 B [10, 2]          out ─┴→ 저장 공간 A [10, 2]

out을 바꿔도 A는 그대로            out을 바꾸면 x가 읽는 값도 바뀜
```

두 경우 모두 처음 읽는 값은 같습니다. 차이는 한쪽을 수정했을 때 나타납니다. 그래서 컴파일러는 값만 맞추는 것으로 충분하지 않습니다. **원래 함께 바뀌던 값은 함께 바뀌고 독립적이던 값은 독립적으로 남아야 합니다.**

`x is y`처럼 같은 파이썬 객체인지 검사하는 것만으로는 이 구분을 할 수 없습니다. 서로 다른 뷰도 메모리를 공유할 수 있고 같은 저장 공간의 서로 다른 위치에서 시작할 수도 있기 때문입니다.

## 3. 컴파일러는 왜 저장 공간을 합치려 할까?

새 텐서를 만들려면 값을 담을 메모리가 필요합니다. 이런 메모리 영역을 버퍼(buffer)라고 합니다. 결과를 따로 만든 뒤 다시 입력에 복사하면 버퍼와 복사 작업이 필요하므로, 컴파일러는 그 과정을 줄일 수 있는지 살펴봅니다.

PyTorch의 Inductor는 이런 최적화를 수행하는 컴파일러입니다. 이 예제의 scatter 연산을 내부에서 다루는 [`_generalized_scatter`](https://github.com/pytorch/pytorch/blob/316140e0fecca99b2133b9d0cb95f8de34213c7a/torch/_inductor/fx_passes/reinplace.py#L92-L123)는 입력을 복제한 뒤 복제본의 일부를 갱신합니다. 아래는 그 동작을 단순화한 코드입니다.

```python
out = inp.clone()
view_of(out).copy_(src)
return out
```

이 결과를 결국 원래 입력에 다시 복사한다면, 처음부터 입력의 해당 부분을 바꾸는 편이 나을 수 있습니다.

```text
원래 흐름: 입력 복제 → 복제본 일부 변경 → 결과를 입력에 다시 복사
줄인 흐름: 입력의 해당 부분을 직접 변경
```

새 결과를 만드는 연산을 입력을 직접 바꾸는 연산으로 되돌리는 최적화가 **제자리 연산 복원(reinplacing)**입니다. 불필요한 복사를 줄일 수 있지만 아무 때나 적용할 수는 없습니다.

처음 예제는 입력에 값을 복사한 뒤에도 `updated`를 반환합니다. 호출자는 `x`와 반환값을 모두 사용할 수 있습니다. 여기서 저장 공간을 합치면 앞 절의 오른쪽 그림처럼 반환값을 바꿀 때 입력도 바뀝니다.

컴파일러가 확인해야 하는 것은 복사를 줄일 수 있는지뿐만이 아닙니다. 따로 만들었던 결과를 이후에 어떻게 쓰는지도 확인해야 합니다.

## 4. 생존성과 탈출 분석은 무엇을 확인할까?

**생존성(liveness)**은 어떤 값이 이후 연산에 필요한지를 따지는 개념입니다. 이전 값을 아무도 사용하지 않는다면 그 값을 보관하던 공간을 다른 용도로 재사용할 여지가 생깁니다. 반대로 나중에 읽을 값이라면 함부로 덮어쓸 수 없습니다.

그런데 함수 안의 사용만 살피면 놓치는 경우가 있습니다. `return updated` 이후에는 함수 안에서 `updated`를 쓰는 코드가 없어도 호출자는 반환값을 계속 사용할 수 있습니다.

이처럼 객체나 참조가 현재 분석하는 범위를 벗어나는지 확인하는 것이 **탈출 분석(escape analysis)**입니다. 이 PR에서는 scatter 결과나 그 저장 공간을 공유하는 뷰가 그래프 출력으로 반환되는지를 확인합니다. 여기서 그래프는 컴파일러가 함수의 연산과 데이터 흐름을 표현한 것이고, 그래프 출력은 그 범위 밖으로 내보내는 결과입니다.

다음 두 코드의 차이를 보겠습니다. `scatter`는 앞의 `slice_scatter`와 같은 종류의 연산을 가리키는 설명용 이름입니다.

```python
# A: independent storage does not escape directly.
y = scatter(x, src)
x.copy_(y)
return y.sum()
```

```python
# B: independent storage is exposed to the caller.
y = scatter(x, src)
x.copy_(y)
return y
```

A에서도 `y`는 입력에 복사된 뒤 `sum`에 사용됩니다. 하지만 호출자가 받는 것은 합계가 들어 있는 새 텐서입니다. `y`의 저장 공간을 직접 받지는 않습니다. 따라서 그래프 내부의 다른 안전성 조건도 만족한다면 제자리 연산 복원을 적용할 수 있습니다.

B에서는 호출자가 `y` 자체를 받습니다. `y`가 `x`와 독립적인지 함수 밖에서도 확인할 수 있으므로 두 저장 공간을 합쳐서는 안 됩니다.

이 때문에 결과를 나중에 쓴다는 이유만으로 최적화를 전부 막는 것도 적절하지 않습니다. **그 값을 계산에 쓰는 것과, 그 메모리를 함수 밖으로 넘기는 것은 다릅니다.**

## 5. 반환값까지 메모리 공유 관계를 따라간다

PR이 추가하는 [`_result_escapes_graph()`](https://github.com/pytorch/pytorch/blob/316140e0fecca99b2133b9d0cb95f8de34213c7a/torch/_inductor/fx_passes/reinplace.py#L222-L239)는 scatter 결과에서 출발해 메모리를 공유하는 연산을 따라갑니다. 그 경로가 그래프 출력에 닿으면 결과가 밖으로 나간다고 판단합니다.

`return updated`만 검사해서는 부족합니다. 다음 코드도 `updated`의 저장 공간 일부를 호출자에게 넘깁니다.

```python
return updated[1:]
```

`split`으로 나눈 결과도 원래 저장 공간을 공유하는 뷰입니다.

```python
a, b = updated.split(2, dim=0)
return a, b
```

이 경우 컴파일러의 FX 그래프에는 `split`의 결과에서 각 항목을 꺼내는 `operator.getitem` 연산이 나타날 수 있습니다. 연산 하나를 나타내는 노드(node) 사이의 연결을 그리면 다음과 같습니다.

```text
scatter → split → getitem(0) → output
                └ getitem(1) → output
```

검사는 `split`에서 멈추지 않고 꺼낸 항목까지 따라가야 합니다. 반면 합계를 구하는 `sum`은 새 결과를 만드므로 같은 저장 공간을 따라가는 경로가 아닙니다.

| 반환하는 것 | 원래 결과의 저장 공간이 밖으로 나가는가? |
| --- | --- |
| `updated` | 결과 자체를 반환하므로 나감 |
| `updated[1:]` | 일부를 바라보는 뷰를 반환하므로 나감 |
| `updated.split(2, dim=0)`의 각 결과 | 저장 공간을 공유하는 뷰이므로 나감 |
| `updated.sum()` | 합계가 들어 있는 새 텐서만 반환하므로 이 경로로는 나가지 않음 |

구현은 검사할 노드를 목록에 넣고 하나씩 꺼내는 깊이 우선 탐색(Depth-First Search, DFS)을 사용합니다. 이미 방문한 노드는 기록해 중복 검사를 피합니다. 이 탐색은 모든 데이터 흐름이 아닌 **저장 공간을 공유하는 연결만 따라갑니다**.

뷰 판별도 연산 이름만 보고 결정하지 않습니다. [`_is_view_op`](https://github.com/pytorch/pytorch/blob/316140e0fecca99b2133b9d0cb95f8de34213c7a/torch/fx/passes/reinplace.py#L25-L33)는 연산의 인자와 메모리 공유 규칙을 선언한 스키마(schema)를 확인합니다. 첫 인자에 별칭 정보가 있고 쓰기 인자로 표시되지 않았는지가 판별 기준입니다. `getitem`은 그 앞 연산이 뷰일 때만 이 탐색 경로에 넣습니다.

## 6. 이득을 따지기 전에 안전한지 확인한다

검사를 추가하는 위치도 중요합니다. 기존 `should_reinplace_scatter()`에는 입력과 출력에 실제 버퍼가 필요하다고 판단하면 제자리 연산 복원을 허용하는 경로가 있습니다.

중간 결과를 실제 메모리에 저장하는 것을 실제 버퍼 생성(realization)이라고 합니다. 주변 연산을 하나로 합치는 연산 융합(fusion)이 가능하다면 중간 결과를 별도 버퍼에 저장하지 않을 수도 있습니다. 하지만 어차피 버퍼가 필요하다면 입력의 버퍼를 재사용하는 편이 유리해 보입니다.

이때 버퍼가 필요하다는 사실만으로 입력과 결과를 합쳐도 되는지는 알 수 없습니다. 반환할 결과 역시 버퍼가 필요하지만, 호출자는 그 결과가 입력과 독립적이기를 기대할 수 있습니다.

그래서 PR은 다른 허용 조건보다 앞에서 탈출 여부를 검사합니다. [`should_reinplace_scatter`의 판정 순서](https://github.com/pytorch/pytorch/blob/316140e0fecca99b2133b9d0cb95f8de34213c7a/torch/_inductor/fx_passes/reinplace.py#L242-L274)를 말로 풀면 다음과 같습니다.

```text
외부에서 가져온 입력인가?
  └ 그렇고, scatter 결과의 저장 공간이 반환되는가?
      └ 그렇다면 제자리 연산 복원을 거절

이 검사를 통과한 경우에만 기존의 다른 허용 조건을 확인
```

코드에서 외부 입력에 해당하는 것은 `placeholder`와 `get_attr`입니다. 각각 그래프의 입력과 속성에서 가져오는 값을 나타냅니다. 호출자가 이 값을 이미 보유하고 있을 수 있으므로 반환 결과가 같은 저장 공간을 쓰면 차이를 관찰할 수 있습니다.

이 검사는 복사 비용을 줄이는 조건보다 먼저 적용됩니다. 결과를 원래 입력에 복사하는 경우만 뒤에서 검사하면 앞선 조건이 이미 최적화를 허용하고 검사를 끝내 버릴 수 있기 때문입니다.

탈출하지 않는다고 모든 최적화가 안전해지는 것은 아닙니다. 그래프 안에서 어떤 값을 언제 읽고 바꾸는지는 기존의 안전성 분석이 계속 확인합니다. 이번 검사는 그 위에 함수 밖의 사용까지 고려하는 조건을 더합니다.

## 7. 테스트도 반환값을 사용해 봐야 한다

처음 표에서 함수 호출 직후의 `x`는 두 실행 모두 `[10, 2]`였습니다. 이 시점에 값을 비교하는 테스트만 있다면 버그를 발견하지 못합니다.

PR의 [회귀 테스트](https://github.com/pytorch/pytorch/blob/316140e0fecca99b2133b9d0cb95f8de34213c7a/test/inductor/test_torchinductor.py#L11911-L12008)는 반환값을 받은 뒤 실제로 수정합니다. 아래는 테스트가 하는 일을 단순화한 코드입니다.

```python
out = candidate(x, src)
out.add_(100)
return x, out
```

이렇게 얻은 `x`와 `out`을 즉시 실행과 컴파일된 실행 사이에서 비교합니다. 반환값을 바꾼 영향이 입력까지 전달되는지 실제 행동으로 확인합니다.

검증 대상은 결과 직접 반환, 결과의 뷰 반환, `split` 결과 반환, 모듈(module) 버퍼 갱신 후 반환, 두 입력에 결과를 복사한 뒤 반환하는 다섯 경우입니다. 반환하는 모양이 달라도 입력과 결과의 독립성이 유지되는지 살펴봅니다.

여기서 모든 출력이 서로 독립적이어야 하는 것은 아닙니다. `split`으로 만든 두 뷰는 원래부터 같은 저장 공간을 공유합니다. 보존해야 하는 것은 원래 프로그램의 공유 관계입니다.

<details markdown="1">
<summary>검증 범위와 clone에 관한 주의점</summary>

PR 작성자는 다섯 하위 테스트가 수정 전 실패하고 수정 후 통과했으며, 추가로 93개 선별 테스트와 47개 관련 테스트를 실행했다고 보고합니다. 로컬 검증은 CPU만을 대상으로 했습니다. CUDA에서도 검증을 마쳤다는 뜻은 아닙니다. [테스트 실행 보고](https://github.com/pytorch/pytorch/pull/195484)

모듈 버퍼 테스트에서는 AOTAutograd가 버퍼를 명시적인 `placeholder` 입력으로 바꿉니다. 그래서 이 테스트가 `get_attr` 분기를 직접 검증하지는 않는다는 [주석](https://github.com/pytorch/pytorch/blob/316140e0fecca99b2133b9d0cb95f8de34213c7a/test/inductor/test_torchinductor.py#L11948-L11955)도 있습니다.

이슈의 [후속 보고](https://github.com/pytorch/pytorch/issues/195451#issuecomment-5480771287)에서는 컴파일한 함수 안에서 `updated.clone()`을 반환해도 문제가 남았다고 합니다. 이는 `clone`이 원래 메모리를 공유한다는 뜻이 아닙니다. `clone`은 새 저장 공간을 만드는 연산입니다. 여러 최적화 단계를 거친 뒤에도 그 동작이 올바르게 유지되는지는 별도로 확인해야 합니다.

보고자는 버퍼 재사용과 복사 제거의 추가 상호작용을 의심했지만, 그 원인을 특정 소스 줄까지 추적하지는 못했다고 밝혔습니다. PR의 탈출 경로 탐색도 `clone`으로 이어지는 연결을 따라가지 않습니다. 이 검사만으로 `clone` 관련 현상까지 모두 설명했다고 볼 수는 없습니다.

</details>
