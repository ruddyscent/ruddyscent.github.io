계산에 쓸 임시 텐서(tensor)를 미리 만들어 두면 반복 호출할 때 메모리를 새로 할당하지 않아도 될 것 같습니다. 그런데 `torch.compile`로 실행하니 준비해 둔 작업 공간(workspace)과 같은 크기의 임시 버퍼(buffer)가 매번 또 생깁니다.

[PyTorch 이슈 #195330](https://github.com/pytorch/pytorch/issues/195330)이 보고한 문제입니다. [PR #195468](https://github.com/pytorch/pytorch/pull/195468)은 이 버퍼 대신 호출자가 준비한 작업 공간을 사용하려 합니다. 다만 작업 공간이 다른 입력과 메모리를 공유하면 계산 결과가 달라질 수 있어 아직 해결해야 할 문제가 남아 있습니다.

왜 중간값을 보관해야 하는지, 이미 준비한 공간을 쓰려면 무엇을 조심해야 하는지 작은 예제로 살펴보겠습니다.

## 1. 이슈: 작업 공간을 줬는데도 메모리를 또 할당한다

다음 함수는 `field`에서 일부 값을 읽어 `gain`을 곱한 뒤 같은 위치에 다시 씁니다.

```python
def dependent(field, indices, gain):
    values = torch.index_select(field, 0, indices) * gain
    field.index_copy_(0, indices, values)
```

`indices`는 읽고 쓸 위치를 담고 있습니다. `index_select`가 그 위치의 값을 모으고 `index_copy_`가 계산 결과를 `field`의 지정한 위치에 복사합니다. 중간값은 `values`에 보관합니다.

그렇다면 중간값을 담을 공간도 미리 만들어서 넘기면 어떨까요?

```python
def preallocated(field, indices, gain, workspace):
    torch.index_select(field, 0, indices, out=workspace)
    workspace.mul_(gain)
    field.index_copy_(0, indices, workspace)
```

`out=workspace`는 읽어 온 값을 기존 `workspace`에 저장하라는 뜻입니다. `mul_`은 새 결과를 만드는 `mul`과 달리 그 안의 값을 직접 바꿉니다. 마지막 줄은 작업 공간에 담긴 결과를 `field`에 복사합니다.

이슈에서는 길이 99인 `float64` 중간값을 사용했습니다. 원소 하나가 8바이트이므로 필요한 공간은 `99 × 8 = 792`바이트입니다. 준비 실행(warm-up)을 마친 뒤 함수를 5번 호출했을 때 결과는 다음과 같았습니다.

| 실행 형태 | 792바이트 할당 횟수 |
| --- | ---: |
| 외부에서 이미 계산한 값을 `field`에 쓰기 | 0 |
| `field`에서 값을 읽어 계산한 뒤 다시 쓰기 | 5 |
| 같은 계산에 미리 만든 `workspace` 사용하기 | 5 |

작업 공간을 넘긴 마지막 경우에도 호출할 때마다 같은 크기의 버퍼를 하나씩 더 할당했습니다. [이슈의 생성 코드 분석](https://github.com/pytorch/pytorch/issues/195330)에 따르면 계산 결과를 새 버퍼에 먼저 저장한 뒤 `field`와 `workspace`에 복사합니다.

이 문제를 이해하려면 우선 중간값을 왜 따로 보관하는지부터 살펴봐야 합니다.

## 2. 스냅샷: 덮어쓰기 전에 계산 결과를 보관하기

다음처럼 같은 위치를 두 번 지정했다고 생각해 보겠습니다.

```text
field   = [10]
indices = [0, 0]
gain    = [2, 5]
```

두 계산 모두 `field[0]`을 읽습니다. 원래 코드처럼 계산을 모두 마친 뒤 `field`에 쓰면 다음과 같습니다.

```python
values[0] = field[0] * 2  # 10 × 2 = 20
values[1] = field[0] * 5  # 10 × 5 = 50
```

두 줄을 계산하는 동안 `field[0]`은 계속 10이므로 중간값은 `[20, 50]`이 됩니다.

반면 중간값을 따로 보관하지 않고 계산할 때마다 바로 덮어쓰면 어떻게 될까요? 다음은 그 차이를 보여 주는 순차 실행 예입니다.

```python
field[0] = field[0] * 2  # 10 × 2 = 20
field[0] = field[0] * 5  # 이미 20이므로 20 × 5 = 100
```

두 번째 계산이 원래 값 10이 아니라 첫 번째 계산으로 바뀐 값 20을 읽습니다. 메모리를 아끼려고 읽기와 쓰기를 합쳤는데 계산까지 달라졌습니다.

**쓰기 전에 필요한 값을 확보해 두면 뒤의 계산이 앞선 쓰기의 영향을 받지 않습니다.** 이 사례에서 말하는 스냅샷 의미론(snapshot semantics)입니다. 중간값을 따로 보관하는 데는 계산 순서를 지키려는 이유가 있습니다.

여기서 설명하는 것은 계산 중에 읽는 값의 차이입니다. 같은 위치에 여러 값을 쓸 때 최종적으로 어느 값이 남는지는 별도 문제입니다. [`index_copy_` 문서](https://github.com/pytorch/pytorch/blob/9cfd54f8bd8a9559416af098da3469b3bade0912/torch/_tensor_docs.py#L2395-L2409)도 그 결과가 쓰기 순서에 따라 달라질 수 있다고 설명합니다. 위 예제가 최종값 50을 보장한다는 뜻은 아닙니다.

## 3. PR의 아이디어: 중간값을 이미 준비한 공간에 저장하기

중간값을 보관해야 한다는 이유는 알았습니다. 하지만 **중간값을 보관하는 일과 그 공간을 새로 할당하는 일은 다릅니다.** 호출자가 이미 `workspace`를 준비했다면 그곳에 저장할 수 있지 않을까요?

PR #195468은 이 부분을 바꾸려 합니다. 기존 방식과 개선안의 차이는 다음과 같습니다.

```text
기존 방식
field에서 읽어 계산 → 새 버퍼에 저장 → field와 workspace에 복사

개선안
field에서 읽어 계산 → workspace에 저장 → field에 복사
```

개선안도 계산 결과를 먼저 모두 저장한 뒤 `field`에 씁니다. 앞 절의 예처럼 계산할 때마다 원본을 바로 덮어쓰는 것이 아닙니다. 스냅샷은 그대로 두고 그 저장 장소만 바꿉니다.

그런데 원래 코드에는 이미 `out=workspace`가 있습니다. 컴파일러는 왜 다른 버퍼를 만들까요?

PyTorch는 컴파일 과정에서 기존 값을 직접 바꾸는 연산을 분석하기 쉬운 형태로 바꿉니다. 이 과정을 함수형 변환(functionalization)이라고 합니다. 이 변환을 거치면 작업 공간에 직접 쓰던 코드도 새 값을 계산한 뒤 나중에 작업 공간으로 복사하는 형태가 될 수 있습니다. 처음 작성한 `out=workspace`가 최종 실행 코드에서 그대로 유지되는 것은 아닙니다.

PR은 조건이 맞는 경우 이 복사를 앞당겨 중간값이 작업 공간에 저장되도록 하고 `field`를 갱신하는 연산이 그 결과를 읽게 합니다. 구체적인 변경은 [복사 위치와 입력 연결을 바꾸는 코드](https://github.com/pytorch/pytorch/blob/9cfd54f8bd8a9559416af098da3469b3bade0912/torch/_inductor/fx_passes/reinplace.py#L1139-L1148)에서 확인할 수 있습니다.

PR에서는 미리 만든 작업 공간을 사용했을 때 792바이트 할당이 사라졌다고 보고했습니다. 작업 공간이 없는 `dependent` 함수에는 필요한 중간 버퍼가 남습니다. [CPU 회귀 테스트](https://github.com/pytorch/pytorch/blob/9cfd54f8bd8a9559416af098da3469b3bade0912/test/inductor/test_cpu_repro.py#L1698-L1745)도 두 경우를 구분해 확인합니다.

이 결과에서 확인한 것은 불필요한 할당의 감소입니다. 프로그램 전체가 얼마나 빨라지는지는 실행 시간을 따로 측정해야 알 수 있습니다.

## 4. 남은 문제: 작업 공간이 다른 입력과 겹칠 수 있다

작업 공간의 크기만 맞으면 언제나 재사용할 수 있을까요? 아직 읽어야 할 입력과 같은 메모리를 쓰고 있다면 곤란합니다.

텐서의 일부를 가리키는 뷰(view)는 데이터를 따로 복사하지 않고 기존 저장 공간을 공유합니다. 다음처럼 하나의 `backing`에서 `gain`과 `workspace`를 만들면 두 영역이 겹칩니다.

```python
gain = backing[:-1]
workspace = backing[1:]
```

어디가 겹치는지 작은 값으로 표시해 보겠습니다.

```text
backing   = [2, 3, 5, 7]
gain      = [2, 3, 5]       # 앞의 세 칸
workspace =    [3, 5, 7]    # 뒤의 세 칸
```

이때 `workspace`의 첫 번째 칸은 `gain`의 두 번째 칸과 같은 메모리입니다. 작업 공간에 결과를 쓰면 뒤의 계산에서 사용할 `gain`까지 바뀝니다. 원래는 계산을 모두 마친 뒤 작업 공간에 복사하던 코드도 복사를 앞당기면 이 문제를 만날 수 있습니다.

이처럼 서로 다른 텐서가 같은 저장 공간을 가리키는 관계를 별칭(alias) 관계라고 합니다. 작업 공간을 재사용하려면 **그곳에 써도 아직 읽을 입력이 바뀌지 않는지** 확인해야 합니다.

PR에는 이를 확인하는 검사가 있지만 호출 사이에 입력 관계가 바뀌는 문제가 남아 있습니다. 첫 호출에서는 `gain`과 `workspace`가 독립적이어서 안전하더라도 다음 호출에서는 위 예처럼 겹치는 뷰가 들어올 수 있습니다. 그런데 처음 만든 실행 코드를 그대로 재사용하면 새 입력에서는 잘못된 결과가 나올 수 있습니다.

[PR #195468의 정확성 제한](https://github.com/pytorch/pytorch/pull/195468)이 바로 이 경우입니다. 관련 [PR #185891](https://github.com/pytorch/pytorch/pull/185891)은 입력의 메모리 겹침 관계가 달라졌는지 검사하고 달라졌다면 다시 컴파일하도록 보완하려 합니다. 작업 공간 재사용은 할당을 줄이는 아이디어만으로 끝나지 않습니다. 다음 호출에서도 안전한 조건이 유지되는지 확인해야 합니다.

## 맺음말

이슈 #195330은 작업 공간을 미리 제공해도 같은 크기의 임시 버퍼가 남는 문제를 보여 줍니다. PR #195468은 필요한 중간값을 그 작업 공간에 직접 저장해 새 할당을 없애려 합니다.

중간값을 없애면 읽는 값이 달라질 수 있지만 중간값을 보관할 장소는 바꿀 수 있습니다. 다만 그 장소에 쓰는 일이 아직 읽을 입력까지 바꾸지는 않아야 합니다. 스냅샷은 유지하면서 작업 공간을 안전하게 재사용하는 것이 이 PR의 과제입니다.
